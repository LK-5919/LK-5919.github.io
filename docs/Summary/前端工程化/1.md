# 构建工具

## Webpack

### webpack 的构建流程

1. 初始化：

   - 首先读取项目中的 `webpack.config.js` 或其他配置文件以获取项目的设置。
2. 解析入口：

   - 根据配置中的 `entry` 属性找到项目的主入口点，这个入口点通常是应用程序的核心模块或捆绑起点。
3. 模块解析与依赖分析：

   - webpack 递归地遍历入口文件及其引用的所有模块，通过 loader 转换非 JS 资源（如 CSS、图片等），并构建一个完整的模块依赖树。
4. 编译阶段：

   - 对每个模块进行编译处理，包括转译（如 Babel 处理 ES6 语法）、压缩优化、tree shaking（去除未使用的代码）等。
5. 生成输出：

   - 根据 `output` 配置，将所有模块打包成一个或多个 bundle 文件，通常包含一个主 bundle 和一些 chunk（按需加载的部分）。
6. 热更新(HMR)：

   - 在开发环境中，当源码发生变化时，webpack 会检测到变化并重新编译受影响的模块及它们的依赖，然后通过 HMR 协议通知浏览器替换更新部分，而不是刷新整个页面。

### Loader

1. 作用：

   - Loader 主要用于预处理文件，将 webpack 不认识的文件类型或者其他非 JavaScript 模块转换为 webpack 能够处理的有效模块。例如，将 `.scss` 文件转换为 `.css`，进一步转换为 CommonJS 模块，或将 `.jsx` 文件转换为普通的 `.js` 文件。
   - Loader 在模块加载的过程中运行，逐个处理导入的文件，每个 loader 可以针对不同的文件类型或者满足特定条件的文件进行转换。
2. 使用方式：

   - 配置在 webpack 配置文件(`webpack.config.js`)的 `module.rules` 数组中，每个 rule 都有一个或多个 loader 的链式调用顺序，从右向左执行。
   - 安装对应的 loader 包，例如 `npm install --save-dev style-loader css-loader sass-loader`。
   - 在配置中指定 loader 时，可以使用 `use` 字段配置，例如：

   ```javascript
   ```

Javascript
1module.exports = {
2  _// ..._
3  module: {
4    rules: [
5      {
6        test: /\.scss$/,
7        use: ['style-loader', 'css-loader', 'sass-loader']
8      }
9    ]
10  },
11  _// ..._
12};

```

### Plugin

1. 作用：
	- Plugin则是对webpack整个构建流程的扩展，它们在不同的编译阶段触发，执行自定义的任务，可以影响到整个构建过程的各个环节，比如打包优化、资源管理、环境变量注入、报告生成、性能分析等。
	- 插件不直接处理单个文件，而是参与到整个构建生命周期中，可以访问并修改webpack内部的状态，甚至控制构建流程。

2. 使用方式：
	- 插件需要在webpack配置文件的`plugins`数组中添加实例化后的插件对象。
	- 安装对应的插件包，例如`npm install --save-dev mini-css-extract-plugin optimize-css-assets-webpack-plugin`。
	- 在配置中启用插件，例如：
	```javascript
Javascript
1const MiniCssExtractPlugin = require('mini-css-extract-plugin');
23module.exports = {
4  _// ..._
5  plugins: [
6    new MiniCssExtractPlugin({
7      filename: '[name].css'
8    }),
9    new OptimizeCssAssetsWebpackPlugin({ _/* options */_ })
10  ],
11  _// ..._
12};
```

### 实现 Loader 或 Plugin

- 实现 Loader： 创建一个自定义的 loader 需要导出一个函数或者一个类，该函数接收源文件内容作为参数，然后返回转换后的结果。Loader 还可以通过 this.query 或 options 参数接收额外的配置信息。例如，一个简单的示例 loader 可能如下：

```javascript
Javascript
1_// my-custom-loader.js_
2module.exports = function (source) {
3  _// 对source进行处理..._
4  return transformedSource;
5};
```

- 实现 Plugin： 一个 webpack 插件需要至少有一个 `apply` 方法，该方法接收一个 compiler 或 compilation 对象作为参数，可以通过该对象注册钩子函数以监听 webpack 生命周期中的各个事件，从而插入自定义逻辑。例如：

```javascript
Javascript
1_// my-custom-plugin.js_
2class **MyCustomPlugin** {
3  **apply**(compiler) {
4    compiler.hooks.emit.tapAsync('MyCustomPlugin', (compilation, callback) => {
5      _// 在emit阶段做些什么..._
6      callback();
7    });
8  }
9}
1011module.exports = MyCustomPlugin;
```

Webpack 中的插件（Plugin）通过在其 `apply` 方法中接收的 `compiler` 或 `compilation` 对象注册各种构建过程中的生命周期钩子函数来干预构建流程。这些钩子涵盖了从初始化到输出文件的全过程，包括但不限于以下几个关键阶段：

1. **Compiler Hooks**

   - `compiler.hooks.run`: 当 webpack 开始运行时触发。
   - `compiler.hooks.watchRun`: 当处于 watch 模式下且文件发生更改重新编译时触发。
   - `compiler.hooks.done`: 编译完成，包括所有模块已编译、优化和输出到文件系统之后触发。
   - `compiler.hooks.beforeRun`: 在实际编译开始前触发。
   - `compiler.hooks.environment`: 当环境准备就绪时触发。
   - `compiler.hooks.afterEnvironment`: 环境变量设置完成后触发。
   - `compiler.hooks.invalid`: 当依赖发生变化导致编译失效时触发。
   - `compiler.hooks.watchClose`: 关闭 watch 模式时触发。
2. **Compilation Hooks**

   - `compilation.hooks.optimizeModules`: 优化模块阶段，可以在这个阶段调整模块及其依赖关系。
   - `compilation.hooks.optimizeChunks`: 优化 chunk 阶段，可以调整 chunk 结构和 chunk 的内容。
   - `compilation.hooks.optimizeTree`: 可以优化模块和 chunk 树结构。
   - `compilation.hooks.optimizeChunkModules`: 用于优化 chunk 内模块。
   - `compilation.hooks.beforeChunks`: 在 chunks 创建之前触发。
   - `compilation.hooks.afterChunks`: 在 chunks 创建之后触发。
   - `compilation.hooks.optimize`: 整体优化阶段。
   - `compilation.hooks.emit`: 文件产出阶段，可以操作最终要输出到硬盘上的文件。
   - `compilation.hooks.additionalAssets`: 添加额外资产阶段，可以在已有文件之外添加更多输出文件。
   - `compilation.hooks.assetEmitted`: 每当一个 asset 被写入到输出目录时触发。
   - `compilation.hooks.seal`: 封印阶段，在此阶段结束后不能再添加新的模块或修改现有模块。
   - `compilation.hooks.chunkHash`: 计算 chunk hash 值时触发。
   - `compilation.hooks.record`: 用于记录状态，常用于持久化缓存数据。

此外，还有许多其他更细粒度的钩子，如与模块相关、与错误和警告相关的钩子等。随着 webpack 版本的更新，其生命周期钩子可能会有所变化和增加，具体可用的钩子列表请查阅最新的 webpack 官方文档。

### Webpack 在生产模式下的构建流程

1. **初始化参数**：

   - Webpack 从配置文件（如 webpack.config.js）和命令行参数中读取并合并参数，形成最终的构建选项。
2. **加载插件和加载器**：

   - 根据配置加载所有注册的插件和 loader，并初始化它们。
3. **寻找入口文件**：

   - 根据配置中的 `entry` 属性定位到项目的入口点，这可能是单个入口文件或多个入口点组成的对象。
4. **模块编译**：

   - 从入口文件开始，Webpack 遍历所有模块依赖树。对于每个模块，它会依次应用匹配到的 loader 进行转换，比如将 ES6 语法转换为 ES5 语法、处理 CSS 和图片资源等。
5. **静态分析与优化**：

   - 在编译过程中，Webpack 执行一系列静态分析和优化操作，例如 Tree Shaking（去除未引用的代码）、Scope Hoisting（减少函数作用域提升开销）、Code Splitting（根据路由或指定拆分点生成多个 chunk）等。
6. **生成 chunk 和 bundle**：

   - 根据模块间的依赖关系创建 chunk，将相关模块组合在一起，并生成最终的 bundle 文件，这些文件通常会被压缩和混淆以优化性能和隐私。
7. **输出资源**：

   - 将处理后的 JavaScript、CSS 和其他资源写入到指定的输出目录，并且可以根据需要生成对应的 HTML 文件，自动注入 bundle 的引用。
8. **资源哈希与缓存控制**：

   - 通常会为产出的资源文件加上内容哈希以支持长期缓存，当文件内容发生变化时，哈希值也会改变，从而避免客户端缓存过期问题。

## Vite

### Vite 的构建流程

Vite 是一种新型的前端构建工具，它充分利用了现代浏览器对于 ES 模块（ESM）的支持来提供快速的开发体验。

1. 服务启动：

   - Vite 在启动时并不会预先进行完整编译，而是直接启动一个 HTTP 服务器，将源码映射到特定的 URL 供浏览器请求。
2. 按需编译与转换：

   - 开发模式下，当浏览器请求模块时，Vite 服务器收到请求后动态编译对应的源码，使用 Rollup 或 Esbuild（默认）进行快速转换，并返回编译后的结果，支持实时热更新。
3. 代理与优化：

   - Vite 提供了高效的模块热更新机制，仅推送更改过的模块到浏览器，浏览器则依据 ESM 规范重新加载对应模块，而非刷新整个页面。
4. 生产构建：

   - 而在生产环境下，Vite 会利用 Rollup 对项目进行一次完整的构建，生成优化后的静态资源，以确保上线的是经过压缩、合并等优化的代码。

在 Vite 的开发模式下，当 Vite 服务器接收到浏览器对项目中模块的请求时，它执行以下操作：

1. 动态编译与转换：

   - Vite 服务器不会预先全部打包项目的所有代码，而是等待浏览器发出请求时才编译对应的单个源文件。
   - 当服务器收到某个模块的请求时，它会立即读取相应的源代码文件（可能是 Vue 组件、React 组件、纯 JavaScript 文件等）。
   - 使用内置的快速编译工具 Esbuild 来对这些源文件进行实时编译，包括转换、转译、优化等工作，如将 TypeScript 编译为 JavaScript、将 JSX 转换为标准 JS、处理 CSS 和其它资源等。
2. 实时热更新：

   - 编译完成后，Vite 服务器将编译好的模块返回给浏览器，浏览器利用原生 ES 模块（ESM）机制加载模块内容。
   - 当开发者修改源代码时，Vite 能够快速侦测到这些变更，并重新编译受到影响的模块，然后通过 WebSocket 或其他方式通知浏览器进行热更新，从而实现实时预览效果。

关于 Esbuild： Esbuild 是一个非常快速的 JavaScript bundler 和 JS/JSX/CSS 等文件的转译工具，由 Go 语言编写而成，具有极高的构建速度。Vite 选择 Esbuild 作为其主要的编译工具，在开发环境和服务端预构建依赖时使用，主要是因为它能够显著提升构建速度，相比于传统的 JavaScript bundlers 如 Webpack 或 Rollup 在开发过程中提供了更快的编译体验。Esbuild 不仅速度快，而且功能全面，支持多种模块格式转换、CSS 处理、Tree Shaking 等。在 Vite 中，Esbuild 被用来加速开发环境下的代码编译和热更新，而在生产环境中，Vite 可能仍然会选择 Rollup 等工具进行最终的优化构建。

Vite 的生产模式下，即当你运行 `npm run build` 或 `vite build` 命令时，Vite 不再依赖于动态编译和按需加载模块。相反，它会执行以下工作流程：

1. 全量编译：

   - Vite 使用 Rollup 作为底层打包工具，对整个项目进行一次性编译。这意味着所有的源代码都会经历编译、转换、优化的过程，包括但不限于 ES 模块转换、CSS 预处理器编译、图片和字体等资源的处理。
2. 静态资源分析与优化：

   - Rollup 会分析项目中的所有模块间的依赖关系，并根据这些关系生成优化过的静态资源。
   - 这包括但不限于：
     - 代码分割（Code Splitting）：将代码划分为多个 chunk，实现懒加载，提高首屏加载速度。
     - Tree Shaking：移除未使用的代码，只保留真正被执行的代码。
     - 压缩与混淆：对 JavaScript、CSS 进行压缩以减小体积，并可根据需要对代码进行混淆以保护源代码。
3. 资源打包与生成：

   - 最终，Vite/Rollup 会将所有必要的资源打包成若干个 bundle 文件，包括主入口文件、异步 chunk 以及 CSS 文件等。
   - 此外，还会生成正确的 HTML 模板，其中包含了指向这些 bundle 文件的链接，确保生产环境下的静态资源正确加载。
4. 静态资源哈希与缓存控制：

   - 生产环境打包时通常会加入文件哈希以利于缓存控制，当资源内容改变时，文件名也随之变化，这样可以确保用户浏览器始终加载最新版本的资源。

### Vite 在生产模式下的构建流程

1. **初始化构建配置**：

   - Vite 同样从配置文件（如 vite.config.js）中获取构建选项，并整合命令行参数。
2. **使用 Rollup 进行构建**：

   - Vite 在生产模式下利用 Rollup 作为打包工具，Rollup 擅长处理 ES 模块并专注于产出高效的、无冗余的代码。
3. **模块解析与转换**：

   - Rollup 会递归地解析入口模块及其依赖，应用合适的插件和转换规则，处理各种类型的模块（JS、Vue、React 组件等）。
4. **Tree Shaking 与优化**：

   - Rollup 具有内置的 Tree Shaking 能力，能够精确地移除未使用的代码块。
5. **代码分割与动态导入**：

   - 支持动态导入和路由级别的代码分割，根据 import()语句生成多个 chunk，实现延迟加载。
6. **资源处理**：

   - 对静态资源进行相应的处理和压缩，如 CSS 压缩、图片优化、字体转换等。
7. **生成静态资产**：

   - 打包完成后，生成优化后的 bundle 和 chunk，同时处理并输出 HTML 文件，确保正确的 script 标签指向 bundle 文件。
8. **资源指纹与缓存控制**：

   - 类似于 Webpack，Vite 在生产构建时也可以通过 rollup-plugin-asset-hash 等插件为资源文件添加内容哈希，用于缓存控制。

## babel 和 polyfill 的作用

在前端工程化中，Babel 和 Polyfill 是两种用于提升代码兼容性的工具，它们分别解决不同层面的问题。

**Babel**:

Babel 是一个 JavaScript 编译器，它的核心作用是将 ES6（ECMAScript 2015）及后续版本中的新语法转换为老版本 JavaScript（通常指 ES5 或更低版本）所支持的语法。例如，当你使用 `class` 关键字定义类、箭头函数、解构赋值、模板字符串等新特性时，Babel 能够将这些语法转换为较老版本浏览器或环境中可识别的形式，确保代码能够在不同的浏览器和环境中正确运行。

**Polyfill**：

Polyfill，则主要用于补充或模拟现代 JavaScript 标准库中新增的功能或 API，这些功能或 API 在旧版浏览器中并未原生支持。例如，Promise、Array.prototype.includes、Map、Set、Fetch API 等都是在 ES6 之后加入的标准库功能，但在许多老版本浏览器中并不可用。Polyfill（如早期的 `@babel/polyfill`，现已被 `core-js` 取代）会在运行时向全局对象添加这些缺失的 API，使得开发者可以提前使用这些新特性，而不必担心兼容性问题。

总结一下：

- **Babel**: 主要是解决语法层面的兼容性问题，通过转译保证新语法能在旧环境中执行。
- **Polyfill**: 主要是解决浏览器内置 API 层面的兼容性问题，通过填充（polyfilling）缺失的 API 实现跨浏览器的一致行为。

在实际项目中，为了更好地优化代码大小和性能，往往推荐更细粒度地使用 polyfill，只引入应用实际所需的最小集合，而不是像早期的 `@babel/polyfill` 那样一次性加载大量兼容性补丁。现在通常的做法是根据目标浏览器的支持情况，结合 `core-js` 和 `@babel/plugin-transform-runtime` 等工具精确引入必要的 polyfill 模块。
