# HTTP code 与 RESTFUL

## 常见 http code

HTTP 状态码是一组三位数代码，它们被 HTTP 协议用来表示客户端与服务器之间的通信结果。以下是 HTTP 状态码按照类别及含义的详细列表。

### 1xx - 信息性状态码 (Informational)

这些状态码表明请求已被接收，正在进行进一步的处理。

- 100 Continue： 表示客户端应当继续其请求，这个临时响应是用来通知客户端其部分请求已经被服务器接收，等待的是请求剩余部分。
- 101 Switching Protocols： 服务器已理解请求，并同意切换到新的协议。

### 2xx - 成功状态码 (Success)

表示请求已经成功被服务器接收、理解并接受。

- 200 OK： 请求已成功，请求的数据也在响应正文中返回。
- 201 Created： 请求已成功处理，并且创建了一个新资源。
- 202 Accepted： 服务器已接受请求，但尚未处理完成（通常异步操作会使用此状态码）。
- 203 Non-Authoritative Information： 服务器成功处理了请求，但返回的信息可能是从第三方获取的，因此可能不可靠或不完整。
- 204 No Content： 服务器成功处理了请求，但不需要返回任何实体内容，且不希望客户端更新缓存。
- 205 Reset Content： 服务器成功处理了请求，但要求客户端重置文档视图（比如清除表单内容）。
- 206 Partial Content： 服务器完成了部分 GET 请求，适用于实现断点续传的分块下载。

### 3xx - 重定向状态码 (Redirection)

需要用户代理采取进一步动作才能完成请求。

- 300 Multiple Choices： 提供多个选项让用户选择，如链接列表。
- 301 Moved Permanently： 被请求的资源已永久移动到新的 URI，未来所有的请求都应该使用新的 URI。
- 302 Found： 请求的资源临时存在于不同的 URI 下，不过客户端应继续使用原有 URI 进行请求（有时用于临时重定向）。
- 303 See Other： 请求的资源可以在另一个 URI 处找到，而且客户端应当采用 GET 方法定向获取资源。
- 304 Not Modified： 客户端发送条件请求（带有 If-Modified-Since, If-Match 等头），如果服务器判断资源未修改，则返回此状态码，告诉客户端可以直接使用本地缓存副本。
- 307 Temporary Redirect： 临时重定向，请求应当重新发送到指定的 URI，但保持原有的 POST/PUT 方法不变。
- 308 Permanent Redirect： 永久重定向，与 301 类似，但是明确规定必须使用相同的请求方法再次发起请求。

### 4xx - 客户端错误状态码 (Client Error)

表明客户端提交的请求包含错误，服务器无法满足请求。

- 400 Bad Request： 服务器无法理解请求，可能是由于语法错误。
- 401 Unauthorized： 请求未经授权，需要验证身份后才能访问。
- 403 Forbidden： 即使经过验证，客户端也没有权限访问所请求的资源。
- 404 Not Found： 服务器找不到请求的资源。
- 405 Method Not Allowed： 客户端使用了服务器不允许的方法请求资源。
- 406 Not Acceptable： 服务器无法提供符合客户端所接受的内容类型。
- 407 Proxy Authentication Required： 类似于 401，但需要通过代理服务器认证。
- 408 Request Timeout： 客户端请求超时。
- 409 Conflict： 由于存在冲突，请求无法完成。
- 410 Gone： 所请求的资源曾经存在，但现在不再可用，并且服务器不知道将来是否会再恢复。
- 411 Length Required： 服务器要求在请求中包含 Content-Length 头部。
- 412 Precondition Failed： 客户端提供的先决条件未满足。
- 413 Payload Too Large： 请求实体过大，超出服务器愿意或能够处理的范围。
- 414 URI Too Long： 请求的 URI 过长，超过了服务器能够处理的最大长度。
- 415 Unsupported Media Type： 客户端上传的媒体类型服务器不支持。
- 416 Range Not Satisfiable： 客户端请求的范围无效，服务器无法提供。
- 417 Expectation Failed： 服务器无法满足 Expect 请求头中的期望值。

### 5xx - 服务器错误状态码 (Server Error)

表明服务器在处理请求过程中遇到错误，无法完成请求。

- 500 Internal Server Error： 服务器遇到了未知错误，无法完成请求。
- 501 Not Implemented： 服务器不支持请求的功能。
- 502 Bad Gateway： 作为网关或代理服务器，从上游服务器接收到无效响应。
- 503 Service Unavailable： 服务器暂时无法处理请求，可能因为过载或维护。
- 504 Gateway Timeout： 作为网关或代理服务器，未能及时从上游服务器获得响应。
- 505 HTTP Version Not Supported： 服务器不支持请求的 HTTP 协议版本。
- 506 Variant Also Negotiates： 在透明内容协商时，服务器存在内部配置错误。
- 507 Insufficient Storage： 服务器无法存储完成请求所需的内容。
- 508 Loop Detected： 发现了无限循环的重定向请求链。
- 510 Not Extended： 服务器不满足请求所需的扩展功能。
- 511 Network Authentication Required： 客户端需要进行网络层身份验证才能获取资源。

## REST 风格

REST（Representational State Transfer，表述性状态转移）是一种软件架构风格，由 Roy Fielding 在其 2000 年的博士论文中提出，用于设计网络应用程序的接口。REST API 是遵循这一风格设计的 Web 服务接口，它充分利用了 HTTP 协议的功能特性，并以资源为中心，强调无状态、可缓存以及系统组件之间相互协作。

以下是对 REST API 风格的主要特点和原则的详细介绍：

1. 资源导向：

   - 在 REST 架构中，每个资源都有一个唯一的标识符，通常表现为 URI（Uniform Resource Identifier），例如 `/users/123` 表示特定用户的资源。
   - 资源可以通过 URI 进行访问、创建、更新和删除。
2. HTTP 方法映射：

   - 使用标准的 HTTP 方法来操作资源：
     - `GET`：用于获取资源，通常是只读操作，且应该是安全的和幂等的。
     - `POST`：用于创建新的资源或者执行一个非幂等操作。
     - `PUT`：用于替换整个资源。
     - `PATCH`：用于更新资源的部分内容。
     - `DELETE`：用于删除指定的资源。
3. 无状态：

   - REST API 应设计为无状态的，这意味着每次请求都应包含所有必要的信息以完成任务，服务器不应该保存客户端上下文信息。这有助于简化服务器设计，提高可伸缩性和可靠性。
4. 统一接口：

   - REST 推崇使用统一的接口结构来处理资源，即对于不同类型的资源，尽管内容可能不同，但处理它们的方式（通过 HTTP 方法）应该是一致的。
5. 层级式结构与链接：

   - 资源可以通过嵌套的 URI 组织成一个层级结构，并且在响应中可以通过链接关系指示其他相关资源的位置。
6. 可缓存：

   - 利用 HTTP 协议的缓存机制，某些响应可以被客户端缓存，从而减少网络延迟和负载。
7. 自描述信息：

   - REST API 的响应中除了包含数据外，还应包括足够的元数据，使得客户端可以根据响应头部和其他元数据自动解析和处理响应内容。
8. 安全性：

   - 通过 HTTPS 和其他安全机制保证传输的安全性，同时通过 OAuth、JWT 等方式进行授权和身份验证。

总结来说，一个设计良好的 REST API 应该清晰、简洁且具有自我描述性，使得开发者无需查看额外文档即可预测出大部分的接口行为。它鼓励松耦合，使得服务端和客户端能够独立演化，并能更好地适应分布式环境下的大规模应用。
